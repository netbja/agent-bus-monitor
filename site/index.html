§ 01What it does

A small bus, a lot of care around it

Everything below ships in this repository. Colours follow busmon's four panels.

  • you, attention
  • bus, activity
  • agents
  • services

Status and directives

Agents publish a declared state and report progress; an agent that drains with subscribe --drain gets them at least once, but streams are capped (~1000 entries) and a plain subscribe skips older ones.

agentbus status · cmd · subscribe

Tracked requests

A request is accepted, blocked or completed on the record, never inferred. busmon lists who owes whom an answer.

agentbus request

4-eyes reviews

A challenge gates a reviewer; each verdict lands in an append-only ledger and a roll-up says approved, rejected or pending.

agentbus challenge · verdict

Wake dispatcher

Nothing polls an agent. When work waits for an idle one, the dispatcher types a one-line wake into its pane, and escalates if nobody answers.

agentbus dispatch

Plan view

A plan file published at a commit shows each task as in review, done or waiting for you, next to the board.

agentbus plan load

Quotas and holds

Usage windows are read from local sources. A provider's agents are held before its limit, and when master's own provider is held the project pauses until the reset; a role can swap to a fallback profile.

agentbus quota · pause · swap

Suspend and resume

Rest every project before a reboot, and bring services and agents back in one gesture.

agentbus suspend · resume --all

Backups

One archive per host: records, files and optionally secrets encrypted with age. Restore checks everything before it writes.

agentbus backup · restore

Notifications

What waits for you reaches your phone or desktop through ntfy, Discord or the desktop, once per event.

agentbus notifications

History

The streams are archived to day files on the host, and searchable by agent, thread or text.

agentbus history

Health checks

Project health is measured, not assumed: missing evidence reads unknown, never ok. Each check says who must act.

agentbus health

Pop agents

The master can pop a specialist role when needed; a finished one is retired and forgotten.

agent-spawn · agentbus retire

Local LLM peer

A local model can join as a read-only test peer, with no shell, no write and no verdict.

agentbus peer

§ 02How it works

Six pictures, one idea each

Role names only: master, coder, foureyes, sentinel. Scroll a figure sideways on a small screen.

Figure 1

Who does what around the bus

The person, the agents and two services meet on one bus.

  • you
  • bus
  • agents
  • services
  • reads and writes
  • types into a pane
What to remember

Everything goes through Redis. busmon and agents are only clients of the bus; the two services are the only automated processes.

Figure 2

The life of a message and the wake line

From a directive to an agent that has read it.

  • write / read
  • typed into the pane
What to remember

The dispatcher types a fixed line, never your message. The content travels through Redis, when the agent drains it. One named exception: after an agent's own declared hand-off it may type the literal /clear.

Figure 3

The dispatcher's decision flow

The rules for one agent, checked in this order, every pass.

  • flow
  • escalation
  • waiting for the pane
  • the one action
What to remember

It prompts only an unarmed agent with something owed, in a pane that is ready, unfocused and proved to be that agent's. Anything else waits, then escalates.

Figure 4

The 4-eyes review and the verdict ledger

Who reviews, where the verdict is kept, and how it is decided.

  • agents
  • bus state
  • not decided yet
  • rejected
  • side effect
What to remember

The ledger is the audit; the gate is only a lock. Ask the ledger whether something was approved, never the gate.

Figure 5

The layers that make a restart safe

What a crash or a reboot does, and does not, lose.

  • data
  • services
What to remember

A service can be killed at any moment. On restart it recomputes from Redis and herdr, and the fences and marks keep it from writing twice. Delivery is not lossless: streams are capped at about 1000 entries, --drain acknowledges after output, a plain subscribe acknowledges older entries unseen, and an agent's turn can be cut.

Figure 6

Suspend and resume

Resting a team and bringing it back.

  • running
  • transition
  • rest state
  • not completed
What to remember

A suspend waits until the team is quiet and keeps a snapshot. A resume is complete only when every required agent is alive again.

§ 03Tour of busmon

The screen you actually work in

Real renders of busmon's dark theme at 140×40, taken from its test goldens. The project, agents and messages are fixture data.

The dashboard

Everything that needs a person comes first.

  • For you lists asks, waits, gates and unread lines.
  • Agents are sorted by attention: state, age, queue, context fill and flags.
  • The lower panel switches between Activity, Board, Requests and Plan (1–4).
  • The header shows the broker, dispatcher and conductor, the pause, and each provider's quota gauges.

Activity, expanded in place

Read a message without leaving the feed.

  • Enter expands a line under itself; Enter again opens the full page.
  • A ● marks what is unread for you; opening it reads it, locally.
  • f pauses auto-scroll, / filters.

The reader

One message, with its kind, sender, target, time and id.

  • n and p step to the next or previous item of the list it came from.
  • y copies the text, Y the whole thread.
  • Long reports keep their full text; the feed shows a one-line preview.

Health

Measured checks, grouped by who has to act.

  • For you, In hand (an agent or a service already handles it) and Not measured; the fine ones fold away.
  • A missing measurement is shown as unknown, never as ok.
  • y copies the command a row suggests.

§ 04Quick start

From clone to a working team

The commands are the README's. The step-by-step guides are in the repository. Operational guide.

  1. Install

    Clones the repository, checks the toolchain, builds the binaries, links the skills and the herdr plugin, and starts the Redis broker.

    $ git clone https://github.com/netbja/agent-bus-monitor && cd agent-bus-monitor
$ ./setup.sh install --install-herdr

  2. Claude Code users: the status line

    Prints the statusLine block to add to ~/.claude/settings.json. Without it the Claude gauges and the context alert have nothing to read. Codex, Grok, Kimi Code and agy need nothing.

    $ agentbus statusline --print-install

  3. Start a team on your project

    Run it in the project's folder. It deduces the project name, yours and the team, asks only for what it cannot deduce, then runs agentbus up and opens the workspace with busmon first.

    $ cd ~/code/myproject && agentbus start
# --yes takes the deduced values, --dry-run shows the plan

  4. Come back later

    Ctrl+B then ↑ opens the Projects picker in herdr. From a shell inside herdr, agentbus up reopens a project and relaunches any agent that is gone.

    $ agentbus up myproject
$ ./setup.sh update
$ ./setup.sh status

§ 05Requirements

What you need

  • v0.x, one operator: one person runs a team of agents on their own machine. Commands and screens still change between releases; there are no accounts and no access control.
  • Linux: developed and used daily; services under systemd --user when available; verified agent identity read from /proc.
  • macOS: builds (a cross-compile run by hand, no CI), not used daily; services under launchd. No agent's process is verified there, so the dispatcher never wakes an agent.
  • Windows: not supported; it does not compile.
  • Go (the version in go.mod, 1.26.3), Git and curl.
  • Docker with Compose, for the redis:8-alpine broker.
  • herdr 0.9.0 or newer; --install-herdr installs it for you.
  • At least one agent CLI: Claude Code, Codex, Grok (beta) or Kimi Code; setup warns, with install pages, when none is found. Only Claude Code resumes a session and reports its context fill; Kimi has no hooks, so its working/idle state is only what it declares.
  • Optional: age, to encrypt secrets in backups.
  • New here? The five-minute quick start, written for Linux.

§ 06Security stance

Documented, and modest

  • The broker is bound to loopback (127.0.0.1:6380), because the password travels in plaintext. Remote access goes through an SSH tunnel.
  • The password lives in a file the installer writes with mode 0600 in a 0700 folder; it reaches redis-server as a config on stdin, never on a command line. A file that exists but cannot be read is an error, never the default.
  • ./setup.sh rotate-redis-password is the person's act: it checks first, and puts the broker and the file back if the new password does not log in.
  • Tests never use the production broker. They run only against an isolated, disposable Redis named by AGENTBUS_TEST_REDIS_URL; an ambient REDIS_URL does not authorise them.
  • Notification targets and their secrets are in a file agentbus never writes and refuses when open to others; every role denies reading or editing it.
  • Every write by the dispatcher and the conductor is fenced by a lease. The dispatcher never runs repository code or agents' commits, with one exception: the opt-in backup.after_command, settable only in config.toml, which the dispatch service's scheduled backup runs after an archive. Only the conductor runs a mission's test commands.
  • It is defence in depth, not a boundary: tool rules match command text, and the bus does not protect you from the local user. The docs say so.
