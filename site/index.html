A multi-agent coordination bus over Redis Streams

agent-bus is a self-contained multi-agent coordination bus over Redis Streams, plus the Go tooling around it. Agents publish status, commands and notifications on a shared Redis instance, under a required project namespace. busmon, a terminal dashboard, shows the traffic live.

The broker, the client and the monitor all live in one repository: one Redis container, two Go binaries and a few scripts, on your own machine. Nothing polls an agent: an idle agent waits on the bus without spending tokens.

Source on GitHub Latest release: v0.27.0 Quick start

What it does

  • Status and directivesA shared bus per project: status, reports, directives and notifications, with at-least-once delivery to each agent (agentbus subscribe).
  • Tracked requestsA request is sent, accepted, blocked or done by its target; acceptance and completion are recorded, never inferred (agentbus request).
  • 4-eyes reviewsA challenge gates an agent until a verdict; the verdict ledger is the audit record (agentbus challenge, verdict).
  • Wake dispatcherA dispatcher types a one-line wake-up into an idle agent's herdr pane when work is waiting, and escalates when nobody answers (agentbus dispatch).
  • Plan viewThe batch's plan, loaded with agentbus plan load, shown by task state in busmon: waiting for you, in review, in progress, upcoming, done.
  • Suspend and resumeagentbus suspend rests a project before a reboot or a long absence, keeps a snapshot, and agentbus resume brings services and agents back (v0.27.0).
  • Backupsagentbus backup writes one archive of every project of the host; agentbus restore verifies it before restoring anything.
  • NotificationsThe dispatch service can tell you what waits for you through ntfy, Discord and the desktop, from targets you configure yourself.
  • Questions to a personAn agent asks, busmon shows the options, your answer wakes it (agentbus ask).
  • Quotas and healthUsage windows are read from local sources; agents are held before the limit. Project health is measured (agentbus health). Tokens are counted, never a cost.

busmon, the terminal dashboard

busmon is the person's screen: what needs you, who does what, and what was said. The panes are For you, Agents, and a lower panel with Activity, Board, Requests and Plan. The text below is the 140-column layout from the project README, on example data.

Without a project name, busmon --list prints the broker's projects and exits:

$ busmon --list
PROJECT             AGENTS  MASTER  LAST ACTIVITY
project-a         6  master  2m ago
agent-bus-monitor        2  -       3h ago
demo                     0  -       23d ago

How it works

Every stream is namespaced {project}:{kind}. Four stream kinds carry the traffic: status, report, notify and cmd. Other keys hold leases, the task board, the 4-eyes ledger and the agents' state.

An agent subscribes with agentbus subscribe, which blocks on the project's cmd stream, prints the first addressed entry and exits. A woken agent runs agentbus subscribe --drain to read what waited. The dispatcher touches only unarmed agents with a real obligation, in a pane that is ready, unfocused and pid-verified. Roles (master, coder, foureyes, sentinel, and pop roles) are defined in roles.toml and launched for Claude Code, Codex and other clients.

Quick start

Linux or macOS, Go (the version in go.mod), Docker with Compose, Git and curl. herdr 0.9.0 or newer is installed for you with --install-herdr. At least one agent CLI is installed by you: Claude Code, Codex CLI, Kimi Code CLI or Grok Build.

git clone https://github.com/netbja/agent-bus-monitor && cd agent-bus-monitor
./setup.sh install --install-herdr     # toolchain check, binaries, skills, herdr plugin, Redis
agentbus statusline --print-install    # Claude Code users: the statusLine block for ~/.claude/settings.json
cd ~/code/myproject && agentbus start   # start a team on your project

agentbus start deduces the project's name, yours and the team, asks only for what it cannot deduce, then runs agentbus up. --yes takes the deduced values and --dry-run shows the plan. Use the commands above rather than herdr plugin install: the plugin needs the broker, binaries and skills that ./setup.sh sets up.

Everyday commands

export AGENT_BUS_PROJECT=myproject
agentbus status claude1 working "plan 10 shipped"
agentbus cmd claude2 run the suite
agentbus subscribe --drain claude1
agentbus agents
busmon --project myproject

Later: ./setup.sh update, ./setup.sh status, ./setup.sh uninstall. agentbus help lists every command.

Requirements

  • Linux or macOS.
  • Go, the version go.mod requires (1.26.3 at this writing).
  • Docker and Docker Compose, for the Redis broker (redis:8-alpine, published on 127.0.0.1:6380).
  • Git and curl.
  • herdr 0.9.0 or newer.
  • At least one agent CLI; the install does not fail without one and lists where to get each.

The 4-eyes review flow

  1. Work is done on a branch. A challenge, agentbus challenge <agent> [--subject S] <why…>, opens a gate on the named agent; the gate blocks it until a verdict.
  2. A verdict is recorded: agentbus verdict --pr 25 --ref <ref> <agent> approve|reject [message]. It is always appended to the {p}:verdicts ledger.
  3. agentbus verdicts --pr 25 prints the roll-up: APPROVED, REJECTED or PENDING (exit 0, 3 or 2). It is approved when the latest independent approval (reviewer different from author) is newer than any rejection. A self-approval is recorded but ignored.
  4. master and the docs agent deliver a reviewed branch with agentbus deliver <branch>, only when the approval names the exact commit (verdict --head).

The gate is only a lock; the ledger is the audit source of truth.

Security stance

  • Loopback broker. The broker is bound to 127.0.0.1:6380. The Redis password travels in plaintext, so the bus is never exposed raw over the network; a remote bus is watched through an SSH tunnel.
  • Password handling. A fresh install writes a random password to ~/.config/agentbus/redis.env (mode 0600). Compose gives it to Redis as a config on stdin, never on a command line.
  • Tests never use the production broker. Integration tests run only against an isolated, disposable Redis named by AGENTBUS_TEST_REDIS_URL; the ambient REDIS_URL does not opt them in.
  • Secrets stay out of settings. config.toml holds no secret and no connection. Notification targets and their tokens live in notify.toml, which you write yourself and agents are denied.
  • Defence in depth, not a boundary. The role tool rules and denies reduce risk; processes an agent starts can still read environment files, and the project documents this.
