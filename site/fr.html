Un bus de coordination multi-agents sur Redis Streams

agent-bus est un bus de coordination multi-agents autonome sur Redis Streams, avec l'outillage Go autour. Les agents publient statuts, commandes et notifications sur une instance Redis partagée, sous un espace de noms de projet obligatoire. busmon, un tableau de bord en terminal, montre le trafic en direct.

Le broker, le client et le moniteur sont dans un seul dépôt : un conteneur Redis, deux binaires Go et quelques scripts, sur votre machine. Rien ne sonde un agent : un agent inactif attend sur le bus sans dépenser de jetons.

Code source sur GitHub Dernière version : v0.27.0 Démarrage rapide

Ce que ça fait

  • Statuts et directivesUn bus partagé par projet : statuts, rapports, directives et notifications, avec une livraison au moins une fois à chaque agent (agentbus subscribe).
  • Demandes suiviesUne demande est envoyée, puis acceptée, bloquée ou terminée par sa cible ; l'acceptation et l'achèvement sont enregistrés, jamais déduits (agentbus request).
  • Revues à quatre yeuxUn challenge verrouille un agent jusqu'à un verdict ; le registre des verdicts sert de trace d'audit (agentbus challenge, verdict).
  • Dispatcher de réveilUn dispatcher tape une ligne de réveil dans le panneau herdr d'un agent inactif quand du travail l'attend, et remonte l'alerte si personne ne répond (agentbus dispatch).
  • Vue du planLe plan du lot, chargé avec agentbus plan load, est affiché par état dans busmon : en attente de vous, en revue, en cours, à venir, terminé.
  • Suspendre et reprendreagentbus suspend met un projet au repos avant un redémarrage ou une longue absence et garde un instantané ; agentbus resume ramène services et agents (v0.27.0).
  • Sauvegardesagentbus backup écrit une archive de tous les projets de l'hôte ; agentbus restore la vérifie avant de restaurer quoi que ce soit.
  • NotificationsLe service dispatch peut vous dire ce qui vous attend via ntfy, Discord et le bureau, vers des cibles que vous configurez vous-même.
  • Questions à une personneUn agent pose une question, busmon montre les options, votre réponse le réveille (agentbus ask).
  • Quotas et santéLes fenêtres d'usage sont lues depuis des sources locales ; les agents sont retenus avant la limite. La santé du projet est mesurée (agentbus health). Les jetons sont comptés, jamais un coût.

busmon, le tableau de bord en terminal

busmon est l'écran de la personne : ce qui a besoin de vous, qui fait quoi, et ce qui a été dit. Les panneaux sont For you, Agents, et un panneau inférieur avec Activity, Board, Requests et Plan. Le texte ci-dessous est la disposition 140 colonnes du README du projet, sur des données d'exemple.

Sans nom de projet, busmon --list affiche les projets du broker et s'arrête :

$ busmon --list
PROJECT             AGENTS  MASTER  LAST ACTIVITY
project-a         6  master  2m ago
agent-bus-monitor        2  -       3h ago
demo                     0  -       23d ago

Fonctionnement

Chaque flux a pour préfixe {projet}:{type}. Quatre types de flux portent le trafic : status, report, notify et cmd. D'autres clés portent les baux, le tableau des tâches, le registre 4-eyes et l'état des agents.

Un agent s'abonne avec agentbus subscribe, qui attend sur le flux cmd du projet, affiche la première entrée qui lui est adressée et se termine. Un agent réveillé lance agentbus subscribe --drain pour lire ce qui attendait. Le dispatcher ne touche que les agents non armés qui ont une vraie obligation, dans un panneau prêt, sans focus et dont le pid est vérifié. Les rôles (master, coder, foureyes, sentinel, et des rôles pop) sont définis dans roles.toml et lancés pour Claude Code, Codex et d'autres clients.

Démarrage rapide

Linux ou macOS, Go (la version de go.mod), Docker avec Compose, Git et curl. herdr 0.9.0 ou plus récent est installé pour vous avec --install-herdr. Au moins un CLI d'agent est à installer par vous : Claude Code, Codex CLI, Kimi Code CLI ou Grok Build.

git clone https://github.com/netbja/agent-bus-monitor && cd agent-bus-monitor
./setup.sh install --install-herdr     # toolchain check, binaries, skills, herdr plugin, Redis
agentbus statusline --print-install    # Claude Code users: the statusLine block for ~/.claude/settings.json
cd ~/code/myproject && agentbus start   # start a team on your project

agentbus start déduit le nom du projet, le vôtre et l'équipe, ne demande que ce qu'il ne peut pas déduire, puis lance agentbus up. --yes prend les valeurs déduites et --dry-run montre le plan. Utilisez les commandes ci-dessus plutôt que herdr plugin install : le plugin a besoin du broker, des binaires et des skills que ./setup.sh installe.

Commandes courantes

export AGENT_BUS_PROJECT=myproject
agentbus status claude1 working "plan 10 shipped"
agentbus cmd claude2 run the suite
agentbus subscribe --drain claude1
agentbus agents
busmon --project myproject

Ensuite : ./setup.sh update, ./setup.sh status, ./setup.sh uninstall. agentbus help liste toutes les commandes.

Prérequis

  • Linux ou macOS.
  • Go, la version exigée par go.mod (1.26.3 à la date de rédaction).
  • Docker et Docker Compose, pour le broker Redis (redis:8-alpine, publié sur 127.0.0.1:6380).
  • Git et curl.
  • herdr 0.9.0 ou plus récent.
  • Au moins un CLI d'agent ; l'installation n'échoue pas sans, et indique où les obtenir.

Le flux de revue à quatre yeux

  1. Le travail est fait sur une branche. Un challenge, agentbus challenge <agent> [--subject S] <pourquoi…>, ouvre un verrou sur l'agent nommé ; il le bloque jusqu'à un verdict.
  2. Un verdict est enregistré : agentbus verdict --pr 25 --ref <ref> <agent> approve|reject [message]. Il est toujours ajouté au registre {p}:verdicts.
  3. agentbus verdicts --pr 25 affiche la synthèse : APPROVED, REJECTED ou PENDING (code de sortie 0, 3 ou 2). Elle est approuvée quand la dernière approbation indépendante (relecteur différent de l'auteur) est plus récente que tout rejet. Une auto-approbation est enregistrée mais ignorée.
  4. master et l'agent docs livrent une branche relue avec agentbus deliver <branche>, seulement quand l'approbation nomme le commit exact (verdict --head).

Le verrou n'est qu'un verrou ; le registre est la source de vérité pour l'audit.

Posture de sécurité

  • Broker en loopback. Le broker écoute sur 127.0.0.1:6380. Le mot de passe Redis circule en clair, donc le bus n'est jamais exposé tel quel sur le réseau ; un bus distant se surveille par un tunnel SSH.
  • Mot de passe. Une installation neuve écrit un mot de passe aléatoire dans ~/.config/agentbus/redis.env (mode 0600). Compose le donne à Redis comme configuration sur l'entrée standard, jamais en ligne de commande.
  • Les tests n'utilisent jamais le broker de production. Les tests d'intégration ne tournent que sur un Redis isolé et jetable désigné par AGENTBUS_TEST_REDIS_URL ; le REDIS_URL ambiant ne les y autorise pas.
  • Les secrets restent hors des réglages. config.toml ne contient ni secret ni connexion. Les cibles de notification et leurs jetons sont dans notify.toml, que vous écrivez vous-même et que les agents n'ont pas le droit de lire.
  • Défense en profondeur, pas une frontière. Les règles d'outils et interdictions des rôles réduisent le risque ; les processus lancés par un agent peuvent encore lire des fichiers d'environnement, et le projet le documente.
