# busmon onboarding: a first-launch tour — design

Status: draft for review (coder, 2026-10-27). Task `onboarding` step 1 (design note and mock-ups,
no code), branch `docs/onboarding-spec`, review subject `onboarding-spec`.

## Decision

Bernard, ask `1793110186603-0` ("Lot suivant"): at busmon's first launch, a few short pages over
the screen: the panels and what they show, writing to an agent, answering a question, the useful
keys, what the header pills mean. Esc skips; a key reopens it; "seen" lives only in the local
cache, never on the bus.

## Behaviour

- **When.** On launch, when the tour marker is absent or older than the tour's version. The marker
  is **one file for the machine**, `~/.cache/agentbus/busmon/_tour.json` (`{"seen": <version>}`;
  step 2 renamed it from `tour.json`, which a project named `tour` would read and overwrite as its own cache;
  0600, written atomically like the per-project cache), not the per-project cache: the panels are
  the same in every project, and a person opening a second project must not see the tour again.
  `--pick` and the CLI paths (`--list`, `--delete`, `--reset`) never show it.
- **Versioned, not nagging.** The tour has a version constant. A release that changes a page's
  meaning bumps it, and the tour then opens once more on **only the changed pages** (each page
  carries the version it last changed in). A wording fix does not bump it.
- **Keys.** `enter` or `→` next, `←` back, `esc` skips the rest; every way out writes the marker
  (a skip counts as seen: the person chose). Mouse: a click on the footer's `next`/`back`/`skip`.
- **Reopen.** In the help (`F1` or `?`), `t` starts the tour from its first page. The help's key
  table gains that row, so the footer and the help advertise it like any other key.
- **Never over a decision.** The tour waits while an ask page, the compose window, a draft, the
  pause popup or the reminder is open (the reminder's own rule), and never opens over a pending
  `waiting` agent's bell: it shows on the next calm update.

## Fit in the Elm shell

- A **modal page stack** like the reader's: `Model.tour` holds the page index and the pages to show
  (`tourPages(version)`), built on the update path with the layout's width; `View` draws the
  centred modal over the shell (as `drawPausePopup` does) and reads nothing else.
- The marker is read once at start in `main` (with the per-project cache) and written by a
  command after the update that closes the tour (`afterUpdate`), never in `View`.
- A new mode, `ModeTour`, with its own key table (`enter`, `→`, `←`, `esc`, `^C`), so the footer
  shows the tour's keys while it is open and no other key acts underneath.

## The text cannot drift from the keys

- **Key cells come from the key tables, by (mode, action).** Each "key — meaning" row names the
  mode whose table holds the key and the action: most are `ModeShell` (`ActAsk`,
  `ActComposeOpen`, `ActRecap`, `ActPlan`, `ActHelp`, `ActRequests`, `ActServices`, `ActHealth`,
  `ActNextUnread`, `ActFilter`, `ActQuit`), others are not: `^O` is (`ModeInput`,
  `ActComposeOpen`), `^S` is (`ModeCompose`, `ActSend`), the digits and `o` (Other) are
  (`ModeShellAsk`, `ActAskPick` / `ActAskOther`). The page renders the binding's `Keys` and `Alt`
  from that mode's table at draw time. Renaming a key changes the tour with it. A test,
  `TestTourKeysExist`, fails when a (mode, action) the tour names has no binding (a removed key
  cannot stay advertised), and `TestTourMentionsNoBareKey` fails when the prose holds a
  key name outside a binding cell (`F4`, `!`, `^S`, …) not produced from the table.
- **Header rows come from the header's functions.** The header page renders each pill with the
  real segment functions (`healthSeg`, `dispatchSeg`, `guardianSeg`, `budgetSeg`, the identity
  pill) on a fixed fixture, so the pill the tour explains is the pill the header draws.
- **Panel names come from the shell** (`frameTitle`'s names, the tab labels): a renamed panel
  renames its row.
- The `U` tokens page and its key join automatically once its binding exists; until then the
  tour does not mention it.

## Pages

1. **Welcome**: what busmon is for; the panels and tabs, one line each; `tab` and the tab keys.
2. **Writing to an agent**: the line (`i`), `@name`, `@all`, Tab completion, the compose window
   (`I`, `^O`, `^S` sends); a broadcast without `@name` needs a second enter.
3. **Answering a question**: the ● in For you, the waiting agent, opening the question (`!`, `w`,
   `F4`), digits, `o` for Other in the compose window; the answer wakes the agent.
4. **Useful keys**: enter (in place, then full text), `u`, `R`, `P`, `/`, `F1`/`?`, `F2`, `F3`,
   `F5`, `q`.
5. **The header**: bus, dispatch, missions, health `!N`, the account window, the person's pill.

## Tests (step 2)

- the tour opens when the marker is absent or older, not when it is current; a skip writes it; a
  second project at the same version does not open it; a version bump opens only the changed
  pages;
- `ModeTour` owns the keyboard (no shell key acts underneath); `F1` then `t` reopens it;
- it waits while an ask, the compose window, a draft, the pause popup or the reminder is open;
- `TestTourKeysExist`, `TestTourMentionsNoBareKey`; the header page uses the real segment
  functions (a golden fails when a pill's text changes and the page does not);
- goldens of each page at 120 and 80 columns in every palette; `TestShellAlignmentSuite` over the
  modal (hostile widths: 60 columns shrinks the modal to the width minus 8 and wraps the prose).

## Settled in review

1. The marker is per machine: the panels are the same in every project (foureyes agrees).
2. `F1` then `t` reopens it: no shell key is spent on a once-a-release action (foureyes agrees).
