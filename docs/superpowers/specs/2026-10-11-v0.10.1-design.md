# v0.10.1 — bound agent identity, two mission minors

- **Status:** design, challenged by Codex (2026-10-11), revised.
- **Base:** `main` @ 542da04 (v0.10.0).
- **Origin:** the v0.10.0 live acceptance (release notes, "Live acceptance — passed").

## 1. Problem

The dispatcher types into a pane only when the agent's snapshot carries a pid and start time
found in the pane's foreground set (`dispatch/decide.go`, rule 6 and `identityOK`). `agentbus
status` records that identity itself (`statusIdent`): the pane from `HERDR_PANE_ID`, the pid from
an ancestor walk.

Codex 0.162 runs every command through a shared `codex app-server` daemon started from another
herdr session. Its commands are never descendants of the pane, and they inherit the daemon's
environment, including a **wrong** `HERDR_PANE_ID`. Its snapshot never gets a pid, so the dispatcher
defers it forever and escalates. The pid check did its job: it refused a pane it could not prove.

## 2. Bound identity

### 2.1 `agentbus bind <agent> --pid <pid> [--pane <pane>]`

It writes the identity fields of `{p}:agents[agent]` (pane, pid, pid_start, terminal) and leaves
state, message, ts and session alone. With no snapshot yet, it creates one with an empty state.

- `--pane` defaults to `HERDR_PANE_ID` and is required outside herdr (`HERDR_ENV` != 1).
- It asks herdr for the pane's foreground processes. `<pid>` must be one of them. It then reads
  the pid's start time and records the herdr terminal id. Anything else exits non-zero and writes
  nothing.
- Without `--pid`, it lists the candidates (pid, ppid, command) and exits 2. There is no heuristic
  pick: a wrapper or shell bound by mistake would survive a client restart and defeat the check.
- `bind` goes through herdr, so whoever binds must reach the herdr socket. That is the same power
  as `herdr pane send-text`, so bind adds nothing to it.

### 2.2 The launcher binds itself

`agent-launch` ends in `os.execvpe` (`scripts/lib/role_config.py`). Exec keeps the pid and its
`/proc` start time (checked: same pid, same field 22). Just before exec, the launcher runs
`agentbus --project <p> bind <agent> --pid <its own pid>` from inside the pane, where the
environment is right. The bound pid is then the client's own process: if the client restarts or
the pane is recycled, the check fails and the agent has to be bound again. A failed bind prints a
warning and the client still starts: an agent the dispatcher cannot wake is better than no agent.

For an agent started by hand (such as Codex in the acceptance), the operator runs
`agentbus bind codex --pane w2:p1`, reads the candidates and binds the client's pid.

### 2.3 `status` keeps a verified identity

The snapshot write moves into one Lua script on `{p}:agents`, shared by `status` and `bind`:

- an **unverified** status (pid 0) takes the existing pane, pid, pid_start and terminal when
  the stored snapshot has a pid. The env pane of an unverified caller is not trusted;
- a **verified** status (its own ancestor walk succeeded) replaces the identity: the caller proved it;
- an entry older than the stored one (ts from the stream id) never replaces state or message.

The stream entry is still written first, and the snapshot remains best effort.

Invariant, written down in the docs: **one runtime per agent name**. A second session using
the same name takes over the bound identity's state.

**Not done:** `CODEX_THREAD_ID`. It names a conversation, not a pane or a process, and its value
is inherited through nested threads. It may come later as optional metadata, but it never
authorises a wake.

## 3. M1 — resolved brief path in load errors

A brief that is missing at the commit is reported as
`brief <as written> (resolved: <path in the change folder>) not found at <commit>`. The source string
stays as written, because it is part of the mission hash.

## 4. M2 — change complete

**When.** Every mission of the current revision that is not aborted is `integrated`. Skipped
counts, and so does a mission kept integrated by a forced reload. Then the conductor runs the
change suite once more on the head of `change/<c>`. That covers the cases where no suite ran on
that head: the last mission was skipped, or the revision changed the suite command.

**Signal.** A cmd entry addressed to the escalation target (`master`), of a new type `complete`,
so the dispatcher wakes master. Its body:
`change <c> rev <n> complete on <branch>@<short head>: <i> integrated, <s> skipped; open the PR to <base>`.

**Exactly once.** One fenced Lua script, under the conductor lease, appends the cmd **and** writes
`completed_rev`/`completed_head` into the change record. A crash leaves either both or neither. A
reload to rev n+1 re-arms it. A red suite records `completed_head` with `complete_failed` and
escalates once; it is retried when the head moves.

The change state stays `active`, because reload and abort rely on it.

## 5. Tests (beyond each unit's own)

- `bind`: pid outside the pane → refused, nothing written; no `--pid` → candidates listed, exit 2;
  recycled pid (other start time) → dispatcher rule 6 "identity mismatch".
- Status merge: unverified after bind keeps the identity; verified replaces it; an older entry
  does not regress state; bind then status in either order gives the same result.
- Launcher: dry-run plan shows the bind; a failed bind still launches.
- M2: only-skipped change; last mission skipped; forced reload of an integrated mission;
  red final suite; the fenced write is atomic (the cmd and the marker exist together or not at all);
  no second `complete` after a conductor restart.
- Live: bind Codex's pane by hand; the dispatcher wakes it with no manual line.
