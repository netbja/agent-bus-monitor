# Hot files: what every PR edits, and a proposal for config/keys.go (waiting for the person)

## Finding/decision

A few files are touched most frequently by merged PRs (the most, CLAUDE.md before its split,
by 36% of them; `docs/operator-notes.md` by 13%, then 34% since 2026-11-07). Shared edits of
the same lines can make two PRs in flight conflict, which the counts alone do not establish;
the rebases do: PRs 489, 494, 495, 499, 500 and 502 were rebased on 2026-11-14 for conflicts
in these files. The first, the operator
notes, is being split into fragments (task operator-notes-fragments). For `config/keys.go`
this note only **proposes**; nothing is refactored until the person chooses.

Files changed by merged PRs, counted by `git diff --name-only <merge>^1 <merge>` over each
first-parent merge of `origin/main`:

**A new setting edits ten shared places**: its entry in `config/keys.go` (appended near the
same lines as every other new key), its line in `config/group.go`'s one map, the ordered name
list in `config/config_test.go`, the literal row count and its comment in
`cmd/agentbus/configcmd_test.go` (`!= 79`, then 80: every pair of settings PRs conflicts
there, as 489/495 and 500 did), `settingLabels` in `cmd/busmon/settings_page.go`, the help map
in `cmd/busmon/settings_ui.go`, and the four settings goldens.

**Proposal for `config/keys.go`, in three steps, each small and separately reviewable:**

1. **No literal count** (smallest, removes the most certain conflict): `configcmd_test.go`
   compares the rows with `config.Keys` (`len(doc.Rows) == len(config.Keys)` and the same
   names), never a number and a comment listing every key.
2. **One place per key**: `Group`, `Label` and `Help` become fields of `config.Key`, set in its
   entry; `config/group.go`'s map, `settingLabels` and the help map go. A new key then edits
   one entry instead of four maps, and `TestEveryKeyHasItsGroup` becomes a check on the field.
3. **One file per area**: the entries move, unchanged, to `config/keys_<group>.go` (display,
   services, backup, notify, health, ...), each appending its keys in an `init` with an
   explicit order field, so `Keys` keeps the page's order. Two features in different areas
   never touch the same file. `config_test.go`'s ordered list becomes a golden file, one key per
   line (a conflict there is a one-line conflict, not the 200-character line of today).

The order matters: 1 alone removes the conflict that recurs on every settings PR; 2 removes
four of the ten places; 3 is a large mechanical move worth doing only if 1 and 2 are not enough.

**The others, briefly** (for later, not proposed in detail here): README.md and the
operational guides could take the fragment approach too (a per-feature section assembled at
release), or be edited only by the docs agent at release; `help.txt` and the settings goldens
are generated (`-update`), so their conflicts are resolved by regenerating, never by hand;
`cmd/busmon/tea_*.go` conflicts come from the message switch in `Update`, which per-feature
handler files would split.

## When it applies

When choosing what to change next about conflicts between PRs in flight, and before adding
a setting: until step 1 lands, two settings PRs in flight conflict on the row count.

## Evidence

- The counts above: `git log origin/main --since=30.days --merges --first-parent` at
  `origin/main` b7a23edc, each merge's first-parent diff, file names counted.
- The rebases of 2026-11-14 on [`cmd/agentbus/configcmd_test.go`](../../../cmd/agentbus/configcmd_test.go)
  and [`config/config_test.go`](../../../config/config_test.go) (PRs 489, 495, 500), and on
  [`docs/operator-notes.md`](../../operator-notes.md) (PRs 494, 495, 502; 502's merge lost a
  paragraph in a web-editor resolution).
- [`config/keys.go`](../../../config/keys.go), [`config/group.go`](../../../config/group.go).

## Limits / what would invalidate it

A count of PRs touching a file is not a count of conflicts: a file edited at distant lines
merges cleanly. The table names where conflicts can happen; the rebases name where they did.
Step 3's value depends on how many settings PRs run in parallel; with one at a time, steps 1
and 2 may be enough. Nothing here is decided: the person chooses which step, if any.
